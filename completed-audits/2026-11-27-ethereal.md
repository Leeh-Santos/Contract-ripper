# Security Audit — Ethereal (NFTfi)

| | |
|---|---|
| **Target** | `targets/ethereal/src/ethereal.sol` — `contract Ethereal` |
| **Type** | NFTfi protocol — ERC-721 "Gems" backed by native ETH or wstETH |
| **Date** | 2026-11-27 |
| **Method** | `detection-agent` (Slither + RAG + call-graph reasoning) → `exploitation-agent` (Foundry PoC on fork/local) |
| **Compiler** | Solc 0.8.28 · OpenZeppelin v5.0.2 |
| **Result** | **1 Critical/High confirmed with a passing PoC**, 2 Medium, 1 Low |

---

## 1. Executive summary

Ethereal mints ERC-721 "Gems" that are each backed 1:1 by either native ETH or
wstETH, chosen per *collection* via an `ethereum` boolean. Users `mint()` by paying a
Gem type's `denomination` and `redeem()` to burn the Gem and reclaim the backing asset
minus a `redeemFee`.

The audit found a **loss-of-funds accounting flaw (C1)** that makes the protocol
insolvent in its intended mixed (ETH + wstETH) deployment: a single `fees` counter is
incremented in **native-ETH wei** by ETH redemptions and in **wstETH token units** by
wstETH redemptions, and `withdrawFees()` pays the whole blended sum out as **native
ETH**. Because wstETH-denominated fees are therefore withdrawn from the native-ETH pool
that backs outstanding ETH Gems, an ordinary owner fee withdrawal drains honest ETH-Gem
holders' backing — and an **unprivileged attacker can arm it on demand** by minting and
redeeming wstETH Gems. This is **confirmed by a passing Foundry PoC** in which a victim's
honest `redeem()` reverts for insufficient ETH.

C1's root cause (two assets, one asset-blind counter) also produces **C2** (wstETH fee
revenue is permanently stranded / `withdrawFees` reverts in wstETH-only deployments).
C3 and C4 are owner-trust and functional-DoS issues respectively.

### Findings at a glance

| ID | Title | Severity | Status |
|----|-------|----------|--------|
| **C1** | Shared `fees` accumulator mixes ETH-wei and wstETH units; `withdrawFees` pays native ETH for wstETH fees → ETH-Gem insolvency | **High** | ✅ **Confirmed (PoC)** |
| C2 | wstETH redemption fees permanently locked; `withdrawFees` reverts in wstETH-only deployments | Medium | Confirmed by mechanism (shares C1 root cause) |
| C3 | Owner trust / mutable critical config enables fund drain and cross-pool mis-redemption | Medium | Identified (owner-gated) |
| C4 | Approved operator (non-owner) cannot redeem | Low | Identified |

## 2. Scope & methodology

**In scope:** `targets/ethereal/src/ethereal.sol` (single file).

**Approach** — the two-agent pipeline:
1. **Detection** — Slither for leads (all reentrancy reports triaged out as false
   positives — see §5), RAG over the vulnerability knowledge base, and manual
   call-graph / invariant reasoning over mint/redeem and the ETH↔wstETH value flows.
2. **Exploitation** — the top candidate was turned into a parameter-free Foundry test
   that deploys the contract locally (no fork needed) and **asserts a broken
   protocol invariant** from unprivileged wallets. A finding is only marked *Confirmed*
   when the PoC passes and would fail against a correct implementation.

**Protocol invariants used as the oracle:**
- Native ETH held ≥ Σ outstanding ETH-Gem denominations (every ETH Gem redeemable).
- wstETH held ≥ Σ outstanding wstETH-Gem balances.
- The ETH and wstETH backing pools are distinct; value must never cross between them.
- `fees` must be a single unit of account, payable only from funds that are **not**
  backing an outstanding Gem.

## 3. C1 — Cross-asset insolvency via shared `fees` accumulator  ·  HIGH  ·  ✅ Confirmed

### Summary
A single `uint256 fees` records redemption fees from **both** asset types, but the two
redemption paths add **different units** to it, and `withdrawFees()` spends it as native
ETH. wstETH-denominated fees are thus paid out of the native-ETH pool that backs ETH
Gems, breaking solvency.

### Affected code
`fees` is asset-blind and written by both paths:

```solidity
// _redeemEth  (native ETH path) — fee is in ETH wei
uint256 redeemFee = (metadata[_tokenId].balance * gems[...].redeemFee) / 1e4;
fees += redeemFee;                      // wei

// _redeemWstEth (wstETH path) — fee is in wstETH token units
uint256 redeemFee = metadata[_tokenId].balance * gems[...].redeemFee / 1e4;
fees += redeemFee;                      // wstETH units  ← same counter, different asset

// withdrawFees — pays the blended sum out as NATIVE ETH
function withdrawFees() external onlyOwner {
    (bool success,) = payout.call{value: fees}("");   // native ETH
    require(success, "Transfer failed");
    fees = 0;
}
```

Note also that `_mintWstEth` forwards the minter's ETH **out** to the wstETH contract,
so wstETH Gems contribute **zero** native ETH to the contract. The only native ETH in
the contract is ETH-Gem backing — exactly the pool `withdrawFees()` draws from.

### Attack path (unprivileged attacker + honest victim)
1. Protocol is configured (by the owner, legitimately) with one ETH-backed collection
   and one wstETH-backed collection.
2. **Victim** mints an ETH Gem for `1e18` → contract holds `1e18` native ETH backing it.
3. **Attacker** (fresh wallet) mints a wstETH Gem (`1e18` ETH is forwarded out to
   wstETH) then redeems it. `_redeemWstEth` does `fees += 5e16` **in wstETH units**.
   Native ETH held is unchanged. Repeat to arm `fees` as large as desired.
4. **Owner** performs a routine `withdrawFees()` → pays the wstETH-unit `fees` out as
   **native ETH**, drawn from the victim's backing.
5. **Victim** tries to `redeem()` → `_redeemEth`'s `msg.sender.call{value: amount}`
   **reverts** for insufficient ETH. The victim's funds are gone.

### Proof of Concept — **PASS**
`targets/ethereal/test/C1.t.sol` — run:

```bash
forge test --match-path targets/ethereal/test/C1.t.sol -vvvv
```

Measured (independently reproduced):

| Quantity | Value |
|---|---|
| ETH backing outstanding (victim gem) before | `1.000e18` |
| `fees` armed by attacker (wstETH units, 2 cycles @ 5%) | `1.000e17` |
| Contract native ETH after owner `withdrawFees()` | **`0.900e18`** |
| Victim net payout owed (`denom − fee`) | `0.950e18` |
| Victim `redeem()` outcome | **REVERTS (insufficient ETH)** |

Invariant broken: `address(ethereal).balance (0.9 ETH) < outstanding ETH-gem backing
(1.0 ETH)`. The test is a *true* proof — under correct per-asset fee accounting the
contract would still hold `1.0e18` ETH and the assertion would fail. A single attacker
cycle already violates `balance ≥ backing`; two cycles are used so the victim's redeem
concretely reverts.

> The PoC deploys a minimal 1:1 **mock wstETH** (via owner `setWstEth`) — the bug is
> pure unit-confusion accounting and needs no real Lido pricing or mainnet fork. Owner
> calls in `setUp()` are legitimate configuration; the exploit is driven by unprivileged
> `attacker`/`victim` wallets, with the owner's own routine `withdrawFees()` as trigger.

### Impact
Loss of user funds / protocol insolvency. Any mixed ETH+wstETH deployment can be driven
insolvent for the native-ETH pool; honest ETH-Gem holders become unable to redeem. No
special privileges are required to arm the condition.

### Recommendation
Track fees **per asset**: separate `ethFees` (wei) and `wstEthFees` (wstETH units), and
have `withdrawFees()` pay each from its own pool (ETH via `call{value:}`, wstETH via
`wstETH.transfer`). Never pay one asset's accrual out of another asset's balance. More
broadly, segregate the ETH and wstETH accounting end-to-end so the two backing pools
can never cross.

## 4. Secondary findings

### C2 — wstETH fees permanently locked / `withdrawFees` reverts (Medium)
Same root cause as C1 from the other direction. wstETH redemptions increment `fees`, but
there is **no code path that ever pays fees out as wstETH**. In a wstETH-only deployment
the contract holds ~0 native ETH, so `withdrawFees()` (`call{value: fees}`) reverts and
all fee revenue is stranded forever. **Fix:** the per-asset accounting in C1 resolves
this — add a wstETH fee-withdrawal path.

### C3 — Owner trust / mutable critical configuration (Medium)
Several owner-only powers are latent rug/footgun vectors:
- `approveWstEth(spender)` grants an **arbitrary spender unbounded wstETH allowance**
  (`type(uint).max`), a drain-all primitive over all wstETH backing.
- `setWstEth(addr)` repoints the backing token at any time.
- `updateCollection(...)` can **flip a live collection's `ethereum` flag**, so Gems
  minted as wstETH (balance stored in wstETH units) would redeem via `_redeemEth` and
  pay **native ETH** from the wrong pool (and vice-versa).

These are owner-gated (trusted-owner model), so not unprivileged-exploitable, but they
should be constrained: make the backing token immutable (or timelocked), scope
`approveWstEth` to a known spender, and forbid changing `ethereum`/`denomination`/
collection on a collection or Gem type that already has circulating Gems.

### C4 — Approved operator cannot redeem (Low)
`redeem()` authorizes via `_checkAuthorized(owner, msg.sender, _tokenId)` (which permits
approved operators), but `_redeemEth`/`_redeemWstEth` then call
`safeTransferFrom(msg.sender, address(this), _tokenId)` with `from = msg.sender`. When
`msg.sender` is an approved operator rather than the token owner, this reverts
`ERC721IncorrectOwner`. Functional DoS for the approval flow; no fund loss. **Fix:**
transfer from the actual `owner` (already resolved via `ownerOf`) rather than from
`msg.sender`.

## 5. Notes on tooling / false positives

Slither's reentrancy reports on `_redeemEth`/`_redeemWstEth`/`withdrawFees` were triaged
out as **not exploitable**:
- `mint` and `redeem` both carry `nonReentrant` (shared guard), so cross-function
  reentry between them reverts.
- State follows checks-effects-interactions — `balance` is zeroed and the token burned
  **before** the ETH `.call`.
- The `safeTransferFrom(msg.sender, address(this), id)` callback lands on the contract's
  own `ERC721Holder.onERC721Received`, not attacker code.
- `withdrawFees` reentrancy is reachable only by the owner/`payout`.

The real bug (C1) is an **accounting/units** defect that static analysis does not flag —
it required invariant reasoning over the two asset pools.

---

## 6. Remediation summary

| ID | Fix |
|----|-----|
| C1 / C2 | Separate per-asset fee accounting (`ethFees` wei, `wstEthFees` units); pay each from its own asset. Segregate ETH and wstETH accounting so pools never cross. |
| C3 | Immutable/timelocked backing token; scoped `approveWstEth`; forbid mutating `ethereum`/`denomination`/collection once Gems circulate. |
| C4 | In `_redeem*`, transfer the token from its actual `owner`, not `msg.sender`. |
